# RULES — Fase 4: Validator Stage

- **Sem código de negócio:** Proibido criar ou modificar código fonte nesta fase.
- **Validação estrita:** Execute fielmente e de forma determinística os comandos declarados no `build_report.md`.
- **Colete Logs:** Obtenha toda a saída do terminal (seja sucesso ou erro) para comprovar a veracidade do teste.
- **Auto-Correção Obrigatória:** Caso aconteça algum erro na fase 4 (validator), a execução NÃO PODE ser interrompida. Você deve registrar a falha temporária no `validation_report.md` e `state.json`, e prosseguir automaticamente para a próxima etapa apropriada (como assumir a Fase 5 de Review e retornar à Fase 3 de Builder) para corrigir o problema. Você deve manter o ciclo rodando de forma autônoma até que a validação passe com sucesso e o fluxo principal seja concluído.
- **Checklist de Validação Estrutural (Skills):** O Validator DEVE confrontar a entrega com os checks de qualidade estrutural, compatibilidade, estilo, performance e segurança correspondentes ao stack do projeto, conforme catalogado em [build-validation-checklist.md](../../skills/build-validation-checklist.md) e demais skills do stack, apontando quaisquer desvios como falhas estruturais de validação.
- **Validação de Restrições e Contratos:** O Validator DEVE verificar se os limites físicos e restrições acordadas na Fase 0 (ex: limite de linhas por arquivo) foram respeitados pelo código gerado, e garantir que todos os artefatos gerados estejam em conformidade com as estruturas H1/H2 definidas nos respectivos contratos.
- **Registro de Guardrails:** Ao concluir a validação, o Validator DEVE registrar no array `prevention_guardrails` do `state.json` quais validações da checklist de build foram executadas com sucesso.
- **Verificação de Conformidade Arquitetural:** O Validator DEVE comparar os nomes de arquivos, contextos, componentes e a estrutura de pastas declarados no `architecture.md` com o código real em `generated/`. Divergências entre o documento e a implementação (ex: nomes de contextos diferentes, subpastas inexistentes, componentes listados mas não criados) DEVEM ser registradas como falhas estruturais. O Validator deve utilizar `list_dir` e `grep_search` para essa verificação.
- **Teto de Score em Ambiente Incompleto:** Se algum comando de execução de testes declarado no `build_report.md` não puder ser executado por ausência de runtime ou dependência de ambiente, o Validator DEVE:
  1. Registrar `ENVIRONMENT_RUNTIME_MISSING` no array `errors` do `state.json`.
  2. Definir o `quality_score.tests` com **teto máximo de 4**, independente da quantidade de testes escritos. Cobertura não executada não pode receber nota alta.
  3. Adicionar na seção `Skipped Checks` do `validation_report.md` um item marcado como `[BLOQUEANTE]` indicando que a run não pode assumir status `completed` até que o ambiente seja corrigido e os testes sejam de fato executados — a menos que o usuário tenha tomado a decisão explícita `"environment_decision": "proceed_without_runtime"` ainda na Fase 0.
  **Exceção Controlada:** Se `"environment_decision": "proceed_without_runtime"` estiver registrado no `state.json`, o Validator aplica o teto de nota mas pode prosseguir sem bloquear a run, registrando isso como risco aceito pelo usuário.
- **Captura de Logs Reais (Stdout):** O Validator é expressamente proibido de simular saídas de teste ou escrever texto estático sobre o resultado. Ele DEVE executar os comandos no terminal e capturar o stdout/stderr real do processo, anexando-o na íntegra no `validation_report.md`. Falhas reais nos testes DEVEM causar bloqueio e rollback automático.
- **Validação de Atalhos de Teclado:** O Validator DEVE confrontar os atalhos de teclado prometidos no `goal.md` com a base de código. Deve-se usar `grep_search` para verificar se as strings de teclas declaradas (ex: `'Delete'`, `'Backspace'`, `'n'`) estão presentes nos handlers de teclado do código fonte. Casos de atalhos prometidos não localizados no código devem gerar falha de validação.
- **Validação Cruzada JSX ↔ CSS:** O Validator DEVE auditar as classes CSS referenciadas na interface. Ele deve identificar as classes estilizadas nos JSX (ou arquivos HTML) e validar, via `grep_search` ou leitura direta dos stylesheets, se existe a correspondente declaração de classe no arquivo CSS. Qualquer classe referenciada na UI que esteja ausente ou órfã no CSS deve ser registrada como uma issue de estilização e falha estrutural.
- **Validação de Interações Compostas:** Se `"complex_interactions"` estiver preenchido em `interview_decisions` no `state.json`, o Validator DEVE auditar cada contrato de isolamento declarado na seção `# Technical Contracts Checklist` do `architecture.md` e registrar o resultado de cada um (`PASSOU` / `FALHOU`) na seção `# Complex Interaction Checks` do `validation_report.md`. Para cada nível de interação contratado, o Validator deve verificar via `grep_search` ou leitura direta do código: (1) se o **ponto de ativação** está implementado no elemento exato declarado no contrato, sem presença em elementos não-intencionados; (2) se o **mecanismo de isolamento** especificado está presente e ativo no código; (3) se a **identificação de tipo** está implementada conforme o contrato. Qualquer item que resulte em `FALHOU` é uma **FALHA ESTRUTURAL** que bloqueia a progressão para a Fase 5, aciona rollback automático para a Fase 3 (Builder) e deve ser registrada no `state.json` e no log de transição com descrição precisa do contrato violado.
