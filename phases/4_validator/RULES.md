# RULES — Phase 4: Validator Stage

- **No Business Code:** Prohibited from creating or modifying source code in this phase.
- **Strict Validation:** Faithfully and deterministically execute the commands declared in `build_report.md`.
- **Collect Logs:** Capture all terminal output (whether success or error) to substantiate the test run validity.
- **Mandatory Self-Correction:** In case of any error in Phase 4 (validator), execution MUST NOT be interrupted. You must record the temporary failure in `validation_report.md` and `state.json`, and automatically proceed to the next appropriate step (such as assuming Phase 5 Review and returning to Phase 3 Builder) to fix the issue. You must keep the cycle running autonomously until validation succeeds and the main flow completes.
- **Structural Validation Checklist (Skills):** The Validator MUST cross-examine the delivery against structural quality, compatibility, style, performance, and security checks corresponding to the project stack, as cataloged in [build-validation-checklist.md](../../skills/build-validation-checklist.md) and other stack-related skills, reporting any deviations as structural validation failures.
- **Constraints and Contracts Validation:** The Validator MUST verify if physical limits and constraints agreed upon in Phase 0 (e.g., lines limit per file) were respected by the generated code, and ensure that all generated artifacts comply with the H1/H2 structures defined in their respective contracts.
- **Guardrails Registration:** Upon completing validation, the Validator MUST record in the `prevention_guardrails` array of `state.json` which validations from the build checklist were executed successfully.
- **Architectural Compliance Verification:** The Validator MUST compare the names of files, contexts, components, and folder structure declared in `architecture.md` with the actual code in `generated/`. Discrepancies between the document and implementation (e.g., different context names, missing subfolders, listed but uncreated components) MUST be recorded as structural failures. The Validator must use `list_dir` and `grep_search` for this verification.
- **Score Ceiling in Incomplete Environment:** If any test execution command declared in `build_report.md` cannot be executed due to the absence of runtime or environment dependency, the Validator MUST:
  1. Record `ENVIRONMENT_RUNTIME_MISSING` in the `errors` array of `state.json`.
  2. Set `quality_score.tests` to a **maximum ceiling of 4**, regardless of the number of tests written. Unexecuted coverage cannot receive a high score.
  3. Add to the `Skipped Checks` section of `validation_report.md` an item marked as `[BLOCKING]` indicating that the run cannot assume `completed` status until the environment is corrected and tests are actually executed — unless the user has taken the explicit decision `"environment_decision": "proceed_without_runtime"` during Phase 0.
  **Controlled Exception:** If `"environment_decision": "proceed_without_runtime"` is recorded in `state.json`, the Validator applies the score ceiling but can proceed without blocking the run, recording this as a risk accepted by the user.
- **Real Logs Capture (Stdout):** The Validator is expressely prohibited from simulating test outputs or writing static text about the result. It MUST run the commands in the terminal and capture the actual stdout/stderr of the process, appending it in full to `validation_report.md`. Real test failures MUST trigger blocking and automatic rollback.
- **Keyboard Shortcuts Validation:** The Validator MUST cross-reference keyboard shortcuts promised in `goal.md` with the codebase. Use `grep_search` to verify if declared key strings (e.g., `'Delete'`, `'Backspace'`, `'n'`) are present in the source code keyboard handlers. Promised shortcuts not located in the code must generate a validation failure.
- **JSX ↔ CSS Cross-Validation:** The Validator MUST audit the CSS classes referenced in the interface. It must identify styled classes in JSX (or HTML files) and validate, via `grep_search` or direct reading of stylesheets, if the corresponding class declaration exists in the CSS file. Any class referenced in the UI that is missing or orphaned in the CSS must be recorded as a styling issue and structural failure.
- **Compound Interactions Validation:** If `"complex_interactions"` is populated in `interview_decisions` within `state.json`, the Validator MUST audit each isolation contract declared in the `# Technical Contracts Checklist` section of `architecture.md` and record the result of each one (`PASSED` / `FAILED`) in the `# Complex Interaction Checks` section of `validation_report.md`. For each contracted interaction level, the Validator must verify via `grep_search` or direct code reading: (1) if the **activation point** is implemented in the exact element declared in the contract, with no presence in unintended elements; (2) if the specified **isolation mechanism** is present and active in the code; (3) if **type identification** is implemented according to the contract. Any item resulting in `FAILED` is a **STRUCTURAL FAILURE** that blocks progression to Phase 5, triggers automatic rollback to Phase 3 (Builder), and must be recorded in `state.json` and the transition log with a precise description of the violated contract.
