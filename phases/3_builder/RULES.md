# RULES — Phase 3: Builder Agent

- **Faithful Implementation:** Strictly follow `task.md` and the implementation plan in `architecture.md`.
- **Focus on Code:** This is the only phase authorized to create/modify code in `generated/` or files in the repository.
- **Consult Coding Guidelines (Skills):** Before writing the first line of code, you are REQUIRED to read and follow the rules in [coding-guidelines.md](../../skills/coding-guidelines.md).
- **Vanilla JS Mastery:** If the project uses pure Vanilla JS (without frameworks), you are required to read [vanilla-js-mastery.md](../../skills/vanilla-js-mastery.md) to shield the application against common anti-patterns.
- **React Best Practices:** If the project uses React or Next.js, you are REQUIRED to read and strictly apply the rules compiled in [AGENTS.md](../../skills/react-best-practices/AGENTS.md) of the `react-best-practices` skill to avoid common performance issues (waterfalls, re-renders), persistence errors (localstorage without handling/debounce), lack of accessibility (absence of Focus Trap in modals), and conflicting styles (recommended use of CSS Modules).
- **Declare Testability:** If tests or validations are added, the Builder is required to define the exact execution commands in `build_report.md`.
- **Consult Stack-Specific Skills:** The Builder is required to load and strictly follow the guidelines and best practices for code, design, security, and platform contained in the skills relevant to the technology stack defined in the Phase 0 decisions (e.g., [web-best-practices.md](../../skills/web-best-practices.md), [react-best-practices](../../skills/react-best-practices/SKILL.md), [vanilla-js-mastery.md](../../skills/vanilla-js-mastery.md), [security-checklist.md](../../skills/security-checklist.md), and [frontend-blueprint.md](../../skills/frontend-blueprint.md)).
- **Compliance with Phase 0 Decisions:** The Builder MUST ensure that all decisions recorded in `interview_decisions` (language, line limits, typography, accessibility, persistence) are implemented and respected in the produced code.
- **Persistence Error Feedback:** Every exception capture block (`catch`) or failure handling involving persistence or critical I/O calls MUST expose clear and friendly visual feedback to the final user in the interface. Hiding errors or limiting them to internal console logs is prohibited.
- **Input Validation and Sanitization:** The Builder MUST apply the structural type validation and data sanitization rules of the security skill to any flow that receives data from external sources before its persistence or processing.
- **Selective Loading of Skills:** To optimize context size and avoid wasting tokens, the Builder MUST consult and read only the files from `skills/` whose identifiers or names directly correspond to the items listed in `loaded_skills` in `state.json`. Reading guidelines from other stacks or unmapped skills is expressively prohibited.
- **Minimum Non-Trivial Test Quota:** The Builder MUST create tests covering at least two types of behavior:
  1. **Pure Business Logic:** Any function executing data transformation, input validation, or isolated business rules (without depending on external I/O) MUST have at least one test case exercising a real flow of input → processing → expected output.
  2. **Critical State Flows:** Operations that alter the main application state (creation, modification, and deletion of core system entities) MUST have at least one test validating the resulting state after the operation.
  **Explicit Prohibition:** Tests that only verify that the test environment is functional (e.g., `assert true == true`, or any assertion without application logic) **DO NOT count** toward the minimum quota and will be classified as trivial smoke tests by the Validator. The Validator MUST reject the Builder's delivery if 100% of the tests are of this type.
  The Builder MUST reference the `Test Strategy` defined in the `planning_summary.md` of Phase 1 to guide what must be tested.
- **Self-Verification of Technical Contracts:** Before reporting build completion, the Builder MUST re-read the `# Technical Contracts Checklist` section of `architecture.md` and actively validate whether each produced file and component perfectly meets the declared contracts.
- **Verification of Planned Tests Presence:** The Builder MUST confirm that all test files listed in the file structure of `architecture.md` (such as hook tests, like `useBoard.test.js`, or components) were actually created in the filesystem and are not empty.
- **Auto-Verification of Compound Interactions:** Before reporting build completion, if `"complex_interactions"` is populated in `interview_decisions` within `state.json`, the Builder MUST execute active verifications for each isolation contract declared in the `# Technical Contracts Checklist` of `architecture.md` and record the results in the `# Complex Interaction Checks` section of `build_report.md`. For each contracted interaction level pair, the Builder must confirm via code inspection (using `grep_search` or direct reading): (1) that the **activation point** of each level is on the correct and unique element defined in the contract, without leaking to unintended parent or child elements; (2) that the **isolation mechanism** defined by the Architect is implemented — if the contract specifies propagation blocking, it must be present; if it specifies type checking, it must occur before processing; (3) that **type identification** is implemented according to the contract, allowing events from different levels to be distinguished at runtime. Any contract marked as `FAILED` blocks build completion and requires immediate correction before proceeding.
