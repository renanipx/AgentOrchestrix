# RULES — Fase 3: Builder Agent

- **Construção Fiel:** Siga estritamente o `task.md` e o plano de implementação do `architecture.md`.
- **Foco em Código:** Esta é a única fase autorizada a criar/modificar código em `generated/` ou arquivos no repositório.
- **Consultar Diretrizes de Código (Skills):** Antes de escrever a primeira linha de código, você é OBRIGADO a ler e seguir as regras em [coding-guidelines.md](../../skills/coding-guidelines.md).
- **Vanilla JS Mastery:** Se o projeto utilizar Vanilla JS puro (sem frameworks), leia obrigatoriamente [vanilla-js-mastery.md](../../skills/vanilla-js-mastery.md) para blindar a aplicação contra anti-patterns comuns.
- **React Best Practices:** Se o projeto utilizar React ou Next.js, você é OBRIGADO a ler e aplicar rigorosamente as regras compiladas em [AGENTS.md](../../skills/react-best-practices/AGENTS.md) da skill `react-best-practices` para evitar problemas comuns de performance (waterfalls, re-renders), erros de persistência (localstorage sem tratamento/debounce), falta de acessibilidade (ausência de Focus Trap em modais) e estilos conflitantes (uso recomendado de CSS Modules).
- **Declarar Testabilidade:** Se forem adicionados testes ou validações, o Builder é obrigado a definir os comandos exatos de execução em `build_report.md`.
- **Consultar Skills Específicas do Stack:** O Builder é obrigado a carregar e seguir rigorosamente as diretrizes e boas práticas de código, design, segurança e plataforma contidas nas skills relevantes ao stack tecnológico definido nas decisões da Fase 0 (ex: [web-best-practices.md](../../skills/web-best-practices.md), [react-best-practices](../../skills/react-best-practices/SKILL.md), [vanilla-js-mastery.md](../../skills/vanilla-js-mastery.md), [security-checklist.md](../../skills/security-checklist.md) e [frontend-blueprint.md](../../skills/frontend-blueprint.md)).
- **Conformidade com Decisões da Fase 0:** O Builder DEVE garantir que todas as decisões registradas em `interview_decisions` (idioma, limites de linhas, tipografia, acessibilidade, persistência) sejam implementadas e respeitadas no código produzido.
- **Feedback de Erros de Persistência:** Todo bloco de captura de exceção (`catch`) ou tratamento de falhas que envolva persistência ou chamadas de I/O críticas DEVE expor um feedback visual claro e amigável ao usuário final na interface. Ocultar erros ou limitá-los a logs internos do console é proibido.
- **Validação de Entradas e Sanitização:** O Builder DEVE aplicar as regras de validação estrutural de tipos e sanitização de dados da skill de segurança a qualquer fluxo que receba dados de fontes externas antes de sua persistência ou processamento.
- **Carregamento Seletivo de Skills:** Para otimizar o tamanho do contexto e evitar desperdício de tokens, o Builder DEVE consultar e ler apenas os arquivos de `skills/` cujos identificadores ou nomes correspondam diretamente aos itens listados em `loaded_skills` no `state.json`. A leitura de diretrizes de outros stacks ou skills não mapeadas é expressamente proibida.
- **Cota Mínima de Testes Não-Triviais:** O Builder DEVE criar testes que cubram no mínimo dois tipos de comportamento:
  1. **Lógica de Negócio Pura:** Toda função que execute transformação de dados, validação de entradas ou regra de negócio isolada (sem depender de I/O externo) DEVE ter pelo menos um caso de teste que exercite um fluxo real de entrada → processamento → saída esperada.
  2. **Fluxos de Estado Críticos:** As operações que alteram o estado principal da aplicação (criação, modificação e exclusão das entidades centrais do sistema) DEVEM ter ao menos um teste que valide o estado resultante após a operação.
  **Proibição Explícita:** Testes que apenas verificam que o ambiente de testes está funcional (ex: `assert verdadeiro == verdadeiro`, ou qualquer asserção sem lógica da aplicação) **NÃO contam** para a cota mínima e serão classificados como smoke tests triviais pelo Validator. O Validator DEVE rejeitar a entrega do Builder se 100% dos testes forem desse tipo.
  O Builder DEVE referenciar a `Test Strategy` definida no `planning_summary.md` da Fase 1 para guiar o que deve ser testado.
- **Autoverificação de Contratos Técnicos:** Antes de reportar a conclusão do build, o Builder DEVE reler a seção `# Technical Contracts Checklist` do `architecture.md` e validar ativamente se cada arquivo e componente produzido atende perfeitamente aos contratos declarados.
- **Verificação de Presença de Testes Planejados:** O Builder DEVE confirmar que todos os arquivos de teste listados na estrutura de arquivos do `architecture.md` (como testes de hooks, como `useBoard.test.js`, ou componentes) foram efetivamente criados no filesystem e não estão vazios.
- **Auto-Verificação de Interações Compostas:** Antes de reportar a conclusão do build, se `"complex_interactions"` estiver preenchido em `interview_decisions` no `state.json`, o Builder DEVE executar verificações ativas para cada contrato de isolamento declarado no `# Technical Contracts Checklist` do `architecture.md` e registrar os resultados na seção `# Complex Interaction Checks` do `build_report.md`. Para cada par de nível de interação contratado, o Builder deve confirmar via inspeção do código (usando `grep_search` ou leitura direta): (1) que o **ponto de ativação** de cada nível está no elemento correto e único definido no contrato, sem vazar para elementos pai ou filho não-intencionados; (2) que o **mecanismo de isolamento** definido pelo Architect está implementado — se o contrato especifica bloqueio de propagação, ele deve estar presente; se especifica verificação de tipo, ela deve ocorrer antes do processamento; (3) que a **identificação de tipo** está implémentada conforme o contrato, permitindo distinguir eventos de níveis diferentes em tempo de execução. Qualquer contrato marcado como `FALHOU` bloqueia a conclusão do build e exige correção imediata antes de avançar.
