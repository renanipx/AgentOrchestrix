# RULES — Phase 5: Reviewer Agent

- **No Code:** Prohibited from writing functional code or scaffolds in this phase.
- **Code Audit (Skills):** The Reviewer MUST read [coding-guidelines.md](../../skills/coding-guidelines.md) and use it as a benchmark to assess whether the Builder wrote simple, surgical code without "overengineering". If the project uses React or Next.js, it is REQUIRED to also validate clean code guidelines and rules present in [react-best-practices](../../skills/react-best-practices/AGENTS.md).
- **Cross-Analysis:** Compare the delivered code and the results of `validation_report.md` against the requirements in `task.md` and the technical plan in `architecture.md`.
- **Clear Verdict:** It is mandatory to issue a clear approval verdict (Approved / Rejected / Needs Adjustment).
- **Syntactic and Semantic Contract Review:** In addition to the code, verify if constraints agreed upon in Phase 0 (such as maximum file size and allowed technologies) were followed by the Builder. Any violation of these constraints must be included in the review.
- **Review based on Stack Skills:** The Reviewer MUST audit the implementation by cross-checking it with the guidelines of the project's stack development skills (e.g., UI, Web, React, TypeScript, Security). Any detected deviation or violation regarding UX, performance, security, or compatibility best practices must be included in the review.
- **Duplicate Logic Review:** The Reviewer MUST flag the presence of repeated logic or functions that could be extracted into helpers or shared utilities, maintaining the simplicity and modularity of the codebase.
- **Mandatory Factual Verification:** Before writing any technical statement in `review.md` about utilized patterns (e.g., "React.memo applied", "useCallback used", "CSS Modules adopted"), the Reviewer MUST run `grep_search` on the source code to confirm the actual presence of the pattern. Statements not verifiable by textual search are PROHIBITED. If the search returns 0 results, the Reviewer must record the absence as an Issue, not as compliance.
- **Cross-Check of Architecture.md:** The Reviewer MUST verify if component names, contexts, and folder structure described in `architecture.md` correspond exactly to the implemented code. Discrepancies must appear in the "Architecture Alignment" section as issues.
- **Selective Loading of Skills:** To optimize context size and avoid wasting tokens, the Reviewer MUST consult and read only the files from `skills/` whose identifiers or names directly correspond to the items listed in `loaded_skills` in `state.json`. Reading guidelines from other stacks or unmapped skills is expressively prohibited.
- **Closing the Risks Loop:** The Reviewer MUST cross-reference the final implementation with the risks listed in `planning_summary.md` (and the initial risk plan). The Reviewer must actively validate in the code if each identified risk was mitigated and record this verification in `review.md`.
- **Technical Contracts Audit:** The Reviewer MUST audit item-by-item the `# Technical Contracts Checklist` section of `architecture.md` against the generated source code. He must list each item of the checklist and explicitly mark it with the status `[PASSED]` or `[FAILED]`.
- **Approval Score Ceiling per Contract:** The Reviewer is expressely PROHIBITED from issuing an approval verdict ("Approved") or assigning any quality score higher than 7 in `state.json` if there is any item marked as `[FAILED]` in the technical contracts checklist or if there are significant architectural deviations without adequate mitigation. If there are contract failures, the verdict must be "Needs Adjustment" or "Rejected", and a corresponding rollback must be triggered.
- **Walkthrough of Compound Interactions:** For functionalities involving multiple interaction levels (when `"complex_interactions"` is populated in `state.json`), the Reviewer MUST produce and document in the `# Interaction Walkthrough` section of `review.md` a step-by-step trace of events for **each interaction scenario** declared. The mandatory format is: `[Scenario] → [Triggered event] → [Active isolation mechanism? GREP confirms: YES/NO] → [Correct type identification? GREP confirms: YES/NO] → [Correct level handler triggered? YES/NO]`. Any step that cannot be confirmed with `YES, confirmed by grep or direct code reading` must be escalated as an **ISSUE** in `review.md` and prevents an `Approved` verdict. Claiming that interactions "are working" or "are fully functional" without completing this walkthrough is a violation of the Factual Verification Rule and is expressely prohibited.
