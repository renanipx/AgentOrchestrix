# RULES — Fase 6: Critic Agent

- **Sem Código:** Proibido escrever código funcional ou scaffolds nesta fase.
- **Foco Arquitetural:** Não aponte problemas simples de sintaxe ou de cobertura direta (já tratados pelo Reviewer). Foque em acoplamento, manutenibilidade, riscos de performance, segurança e escala.
- **Seniordade:** Assuma um papel crítico com visão de longo prazo sobre o projeto.
- **Auditoria Baseada em Boas Práticas (Skills):** Para sua análise crítica sobre segurança, performance, acessibilidade e arquitetura web, embase-se nas diretrizes em [web-best-practices.md](../../skills/web-best-practices.md) e, se o projeto usar Vanilla JS, pontue melhorias baseadas em [vanilla-js-mastery.md](../../skills/vanilla-js-mastery.md). Caso o projeto utilize React ou Next.js, é OBRIGATÓRIO basear sua crítica avançada nas diretrizes de [react-best-practices](../../skills/react-best-practices/AGENTS.md).
- **Escalação com Ação Concreta:** Para cada risco identificado, o Critic DEVE classificá-lo explicitamente com uma etiqueta de severidade (`[ALTA]`, `[MÉDIA]` ou `[BAIXA]`) e obrigatoriamente fornecer uma proposta concreta e acionável de mitigação, indicando bibliotecas específicas ou padrões de design aplicáveis. Apontar riscos vagos ou genéricos sem mitigação proposta é PROIBIDO. Além disso, se houver melhoria no critic, deve-se questionar o usuário se ele deseja resolver este problema na run atual ou em uma run de refatoração futura, e levantar a criticidade.
- **Análise de Acoplamento de Estado:** O Critic DEVE avaliar a arquitetura de estado e comunicação do sistema para detectar dependências acopladas ou bidirecionais entre componentes de estado global, classificando acoplamentos circulares ou bidirecionais como risco `[ALTA]` e propondo padrões de desacoplamento adequados.
- **Análise de Cobertura de Testes:** O Critic DEVE avaliar a ratio de cobertura de testes (unitários, integração, E2E) e classificar a situação por severidade: (a) `[ALTA]` se <20% das funções/componentes possuem testes, (b) `[MÉDIA]` se entre 20-60%, (c) `[BAIXA]` se >60%. O Critic DEVE recomendar áreas prioritárias para aumento de cobertura baseado no risco funcional.
- **Atualização do Quality Score com Evidência:** Ao concluir a análise, o Critic DEVE preencher o objeto `quality_score` no `state.json` com notas de 0 a 10 para cada dimensão, seguindo a rubrica definida no [HEARTBEAT.md](../../HEARTBEAT.md) (Seção 4.3). Para notas ≥ 8, o Critic DEVE incluir justificativa explícita no `critic.md` com evidências do código. É PROIBIDO atribuir nota 10 a qualquer dimensão se o próprio artefato de crítica identificar riscos ou lacunas nessa dimensão. Se o Critic identificar cobertura de testes < 60%, a nota de `tests` NÃO pode exceder 6.
- **Diagnóstico com Grau de Implementabilidade:** Para cada mitigação proposta, o Critic DEVE classificá-la como:
  - `[TRIVIAL]`: Pode ser implementada em < 10 linhas de código. O Critic DEVE recomendar que a run retorne à Fase 3 para aplicação imediata.
  - `[MODERADA]`: Requer alteração significativa. Deve ser incluída no Actionable Backlog para próxima run.
  - `[COMPLEXA]`: Requer decisão arquitetural. Deve gerar uma run dedicada de refatoração.
- **Bloqueio Obrigatório por Risco Alto:** Se o `critic.md` registrar ao menos 1 risco classificado como `[ALTO]`, o Critic é **PROIBIDO** de definir `"status": "completed"` no `state.json`. O status DEVE ser obrigatoriamente `"waiting_for_user"`. O agente DEVE perguntar ao usuário no chat, de forma clara e objetiva:
  - Se deseja retornar à fase correspondente para resolver o risco na run atual.
  - Se deseja encerrar a run e tratar o risco como item do Actionable Backlog de uma run futura.
  A run só pode transitar para `"completed"` após a escolha explícita do usuário.
- **Papel Adversarial Oblíquo:** O Critic DEVE agir como um testador adversário implacável. Ele deve analisar e prever o comportamento do sistema diante de condições extremas: (a) cliques ou chamadas de API repetidas e sequenciais em curtíssimo intervalo (concorrência rápida), (b) dados de entrada no limite superior ou malformados, (c) falhas e quedas repentinas de localStorage ou I/O, (d) renderização sob telas de dimensões atípicas.
- **Mapeamento Mínimo de Riscos:** O Critic DEVE listar e detalhar obrigatoriamente no mínimo 3 riscos ocultos (`Hidden Risks`) sob a base de código gerada. Descrever apenas 1 ou 2 riscos é considerado auditoria complacente e viola a regra de consistência.
- **Independência Crítica:** O Critic é expressamente proibido de apenas resumir, concordar ou parafrasear o que o Reviewer e o Validator relataram. O Critic DEVE re-ler autonomamente todo o código-fonte gerado e os artefatos técnicos para identificar vulnerabilidades estruturais ou desvios que passaram despercebidos pelas fases anteriores.
- **Análise Adversarial de Interações Compostas:** Para projetos com `"complex_interactions"` preenchido em `interview_decisions`, o Critic DEVE executar obrigatoriamente a seguinte análise adversarial sobre o código-fonte: (1) Mapear todos os pontos de ativação de interação em cada nível hierárquico (via `grep_search` pelos identificadores de handlers ou atributos de interação relevantes ao stack); (2) Mapear todos os handlers de resposta às interações em cada nível; (3) Cruzar os dois mapas para detectar se um evento destinado a um nível pode ser interceptado, propagado ou processado por um handler de outro nível, criando comportamento ambíguo, duplicado ou incompleto. Se identificado qualquer conflito de handlers entre níveis, o risco DEVE ser classificado como `[ALTA]` e o status da run DEVE ser definido como `waiting_for_user`, bloqueando a transição para `completed` sem decisão explícita do usuário.
