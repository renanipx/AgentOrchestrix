# RULES — Fase 2: Architect Agent

- **Alinhamento Técnico:** Desenhe a arquitetura baseando-se estritamente no `task.md`.
- **Fim da Fase (Comportamento por Comando):** Se o comando for `orquestrar:`, altere a fase para `3_builder` no `state.json` e continue automaticamente a execução da implementação. Se o comando for `planejar:`, gere também o artefato consolidado `runs/run-XXX/artifacts/planning_summary.md` contendo links e resumos dos 3 artefatos gerados (`goal.md`, `task.md`, `architecture.md`), pare a execução, mude o status do `state.json` para `completed` e apresente os artefatos gerados.
- **Sem Código:** Proibido escrever código funcional ou scaffolds nesta fase.
- **Análise de Atrito de Restrições:** Ao desenhar a arquitetura, correlacione as decisões de escopo e tecnologia com as restrições definidas na Fase 0. Se houver restrições estritas de tamanho de arquivo ou complexidade, você é OBRIGADO a propor uma arquitetura modularizada com isolamento de escopo/estado para mitigar acoplamento excessivo.
- **Design e Arquitetura (Skills):** Caso o projeto envolva uma interface visual (UI) ou desenvolvimento Web/React/etc., o Architect DEVE consultar as skills correspondentes ao stack definido (ex: [frontend-blueprint.md](../../skills/frontend-blueprint.md), [react-best-practices](../../skills/react-best-practices/SKILL.md), [web-best-practices.md](../../skills/web-best-practices.md)) para guiar o design de componentes, ciclo de vida e renderização.
- **Separação de Contextos de Estado:** O Architect DEVE planejar a separação dos contextos de estado por domínio ou responsabilidade para evitar re-processamento desnecessário, conforme as diretrizes do stack selecionado.
- **Checklist de Interações e Acessibilidade:** O Architect DEVE mapear no design todas as interações complexas planejadas e especificar a biblioteca acessível ou o fallback programático para garantir suporte universal (mouse, teclado e touch).
- **Avaliação de Limites de Storage:** Caso o armazenamento seja em disco ou cliente, o Architect DEVE planejar de acordo com as restrições físicas de capacidade do storage selecionado e propor estratégias de migração ou exportação de dados.
- **Estratégia de Performance e Cache:** Para componentes que processam coleções de dados dinâmicas ou pesadas, o Architect DEVE definir no `architecture.md` a estratégia de renderização otimizada, cache e memoização recomendada para o stack.
- **Lógica de Efeitos e Ciclo de Vida Estáveis:** O Architect DEVE identificar e documentar fluxos de efeitos colaterais e persistência, especificando que dependências dinâmicas sejam controladas de forma estável para evitar loops.
- **Catálogo de Funções Utilitárias:** O Architect DEVE listar no `architecture.md` as funções utilitárias e utilitários compartilhados necessários, definindo suas responsabilidades para evitar que o Builder crie lógica duplicada.
- **Checklist de Contratos Técnicos:** O Architect DEVE obrigatoriamente criar uma seção denominada `# Technical Contracts Checklist` no `architecture.md`. Essa seção deve listar asserções técnicas estritas por componente ou arquivo planejado (ex: "Card.jsx: deve usar useEffect para sincronizar estado local com props do pai", "Board.jsx: deve implementar handlers de drag-and-drop para colunas"). Esses itens servirão de input obrigatório para verificação nas fases do Builder, Validator e Reviewer.
- **Contratos de Interações Compostas:** Ao projetar componentes que envolvam múltiplos níveis de elementos interativos (ativado quando `"complex_interactions"` estiver preenchido em `interview_decisions`), o Architect DEVE especificar **obrigatoriamente** os seguintes itens no `# Technical Contracts Checklist` do `architecture.md` para cada par de níveis: (1) **Ponto de Ativação:** Qual elemento exato (e apenas ele) é o ponto de entrada da interação de cada nível, para que não haja ambiguidade de ativação (ex: o elemento correto que inicia o gesto/clique/foco, evitando que o container pai ou filho incorreto responda ao evento); (2) **Mecanismo de Isolamento:** Qual mecanismo de bloqueio de propagação de evento é usado para garantir que a interação de um nível não ative handlers de outro nível (ex: `stopPropagation`, condições de guarda baseadas em tipo ou origem do evento, ou verificação de metadados antes de processar); (3) **Identificação de Tipo:** Como o sistema distingue eventos provenientes de níveis diferentes em tempo de execução, garantindo que o handler correto sempre processe o evento correto. Sem esses 3 itens por par de nível presentes e explicitamente declarados no checklist, a fase Architect não pode ser encerrada.
