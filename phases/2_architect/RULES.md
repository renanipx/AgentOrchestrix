# RULES — Phase 2: Architect Agent

- **Technical Alignment:** Design the architecture basing it strictly on `task.md`.
- **End of Phase (Behavior by Command):** If the command is `orchestrate:`, the transition can occur directly or, preferably, by following the recommended handoff at the end of Phase 2 (as per the HANDOFF EXCEPTION in [AGENTS.md](../../AGENTS.md)): generate `artifacts/handoff.md`, set the run status to `waiting_for_user` in `state.json`, and instruct the user to open a new clean chat running `continue-run: runs/run-XXX`. If the command is `plan:`, also generate the consolidated artifact `runs/run-XXX/artifacts/planning_summary.md` containing links and summaries of the 3 generated artifacts (`goal.md`, `task.md`, `architecture.md`), stop execution, change the status of `state.json` to `completed`, and present the generated artifacts.
- **No Code:** Prohibited from writing functional code or scaffolds in this phase.
- **Constraints Friction Analysis:** When designing the architecture, correlate scope and technology decisions with the constraints defined in Phase 0. If there are strict file size or complexity constraints, you are REQUIRED to propose a modular architecture with scope/state isolation to mitigate excessive coupling.
- **Design and Architecture (Skills):** If the project involves a visual interface (UI) or Web/React/etc. development, the Architect MUST consult the skills corresponding to the defined stack (e.g., [frontend-blueprint.md](../../skills/frontend-blueprint.md), [react-best-practices](../../skills/react-best-practices/SKILL.md), [web-best-practices.md](../../skills/web-best-practices.md)) to guide component design, lifecycle, and rendering.
- **Separation of State Contexts:** The Architect MUST plan the separation of state contexts by domain or responsibility to avoid unnecessary re-processing, according to the guidelines of the selected stack.
- **Interactions and Accessibility Checklist:** The Architect MUST map all planned complex interactions in the design and specify the accessible library or programmatic fallback to ensure universal support (mouse, keyboard, and touch).
- **Storage Limits Evaluation:** If storage is client-side or on-disk, the Architect MUST plan according to the physical capacity constraints of the selected storage and propose data migration or export strategies.
- **Performance and Cache Strategy:** For components processing dynamic or heavy data collections, the Architect MUST define in `architecture.md` the recommended optimized rendering, caching, and memoization strategy for the stack.
- **Stable Side-Effects and Lifecycle Logic:** The Architect MUST identify and document side-effect and persistence flows, specifying that dynamic dependencies are stably controlled to avoid loops.
- **Utility Functions Catalog:** The Architect MUST list the required utility functions and shared utilities in `architecture.md`, defining their responsibilities to prevent the Builder from creating duplicate logic.
- **Technical Contracts Checklist:** The Architect MUST create a section named `# Technical Contracts Checklist` in `architecture.md`. This section must list strict technical assertions per component or planned file (e.g., "Card.jsx: must use useEffect to synchronize local state with parent props", "Board.jsx: must implement drag-and-drop handlers for columns"). These items will serve as mandatory input for verification in the Builder, Validator, and Reviewer phases.
- **Compound Interactions Contracts:** When designing components involving multiple levels of interactive elements (activated when `"complex_interactions"` is populated in `interview_decisions`), the Architect MUST **obligatorily** specify the following items in the `# Technical Contracts Checklist` of `architecture.md` for each pair of levels: (1) **Activation Point:** Which exact element (and only that one) is the entry point of the interaction of each level, so there is no activation ambiguity (e.g., the correct element that starts the gesture/click/focus, preventing the incorrect parent or child container from responding to the event); (2) **Isolation Mechanism:** What event propagation blocking mechanism is used to ensure that interaction at one level does not trigger handlers of another level (e.g., `stopPropagation`, guard conditions based on event type or origin, or metadata check before processing); (3) **Type Identification:** How the system distinguishes events coming from different levels at runtime, ensuring that the correct handler always processes the correct event. Without these 3 items per level pair present and explicitly declared in the checklist, the Architect phase cannot be closed.
