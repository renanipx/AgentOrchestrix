# Build Validation Checklist

This guide defines the automatic, structural, and quality validations that the Validator (Phase 4) and the Builder (Phase 3) must execute on the project's source code to ensure technical compliance.

---

## 1. Web, HTML & SEO

### 1.1 Metatags and Language Verification
- **Target File:** `index.html` (or main entry file).
- **Mandatory Checks:**
  - The `<html lang="...">` element must exist and contain the correct language code corresponding to the one defined in the Phase 0 interview (e.g., `lang="en"`).
  - The `<title>` element must exist and contain the specific project name. Standard or automatically generated texts (e.g., "generated", "Vite App", "React App") are expressely prohibited.
  - The `<meta name="description" content="...">` element must exist and concisely describe the application relevance.

*Suggested Validation Command:*
```powershell
# Search SEO tags
grep_search -Query "<title>" -SearchPath "<run_generated_path>"
grep_search -Query "name=\"description\"" -SearchPath "<run_generated_path>"
```

### 1.2 Fonts and External Assets Matching
- **Mandatory Check:**
  - For each custom typographic font declared in CSS style files via `font-family` (e.g., `Outfit`, `Inter`, `Poppins`), there must be a corresponding `<link>` element or `<style>` tag in the HTML that loads the font (via Google Fonts or another reliable CDN).
  - Fonts declared but not loaded constitute a structural failure.
  - **Bidirectional Check:** For each font loaded via `<link>` in the HTML (e.g., Google Fonts), there must be at least one reference to that font in `font-family` within the CSS files. Fonts loaded but never referenced in the CSS constitute a structural failure (wasted resources and unnecessary latency).

*Suggested Validation Command:*
```powershell
# Search font declarations in CSS
grep_search -Query "font-family" -SearchPath "<run_generated_path>"
```

## 2. TypeScript & General Code Quality

### 2.1 Strict Typing (TypeScript)
- **Mandatory Check:**
  - The use of forced casting to `as any` is prohibited in `.ts` and `.tsx` files.
  - Prefer explicit types, Union Types, or Type Guards (`if (isType(x))`).

*Suggested Validation Command:*
```powershell
# Search for "as any"
grep_search -Query "as any" -SearchPath "<run_generated_path>"
```

### 2.2 Unique IDs Generation
- **Mandatory Check:**
  - Client-side generated IDs must not use simple, insecure generators based only on time or simple statistics (such as `Date.now()` or `Math.random()`).
  - IDs must be robustly generated by dedicated APIs, such as `crypto.randomUUID()` or specific libraries (such as `uuid`).

*Suggested Validation Command:*
```powershell
# Search for weak generators
grep_search -Query "Date.now()" -SearchPath "<run_generated_path>"
grep_search -Query "Math.random()" -SearchPath "<run_generated_path>"
```

### 2.3 Persistence Handling and Logs
- **Mandatory Check:**
  - Persistent write operations (such as `localStorage.setItem` or API connections) that have `catch` blocks must not only log to the console (`console.error`/`console.warn`). They must trigger some visual notification in the UI (toast, modal, banner) to keep the user informed.

*Suggested Validation Command:*
```powershell
# Search for silent error handlers
grep_search -Query "console.error" -SearchPath "<run_generated_path>"
```

## 3. Interfaces & Frameworks (React/Next.js)

### 3.1 Unnecessary React Imports
- **Mandatory Check:**
  - In modern environments with React 17+ (active JSX Transform), explicit imports of `React` (e.g., `import React from 'react'`) in files containing only JSX are unnecessary and must be cleaned up, except when specific hooks are loaded from it (e.g., `import React, { useState } ...`).

*Suggested Validation Command:*
```powershell
# Search for unnecessary imports
grep_search -Query "import React from" -SearchPath "<run_generated_path>"
```

### 3.2 Stable Hook Dependency Arrays
- **Mandatory Check:**
  - Verify that callbacks or functions passed to dependency arrays of hooks like `useEffect`, `useMemo`, or `useCallback` are stable (stabilized via `useCallback` or stored in `useRef`). Functions recreated on every render cause side-effect loops and performance issues.

---

## 4. UX and CSS (Visual)

### 4.1 Animation Pairs
- **Mandatory Check:**
  - Dynamic components that display an entrance animation (e.g., fade-in, slide-in) must obligatorily have a corresponding smooth exit animation (e.g., fade-out, slide-out) before their removal/disappearance from the DOM. Abrupt disappearances constitute UX failure.

### 4.2 Responsive Visual Controls
- **Mandatory Check:**
  - Secondary actions displayed on hover in tables or cards (such as delete or edit buttons) must support touch devices. Verify the existence of `@media (hover: none)` directives ensuring that hover controls are always visible on touch screens.

---

## 5. Build Output & Bundle Analysis

### 5.1 Bundle Size Recording
- **Mandatory Check:**
  - The `validation_report.md` MUST record the total size of the JS and CSS bundle (raw and gzip) as output by the production build.
  - If the run is an iteration of a previous run with the same objective, the Validator MUST compare the sizes and justify any increase > 5%.

### 5.2 Dead Code Verification
- **Recommended Check:**
  - Search for unused imports using build output analysis (transformed modules vs declared modules).

## 6. Compound Interactions (Multiple Hierarchical Levels)

This section is activated when `"complex_interactions"` is populated in `interview_decisions`. The checks below must be executed using the contracts declared in the `# Technical Contracts Checklist` section of `architecture.md` as reference, adapting the commands to the project's stack and language.

### 6.1 Verification of Activation Points

- **Mandatory Check:** For each contracted interaction level, verify that the interaction activation point (e.g., the element starting a gesture, click, or focus) is implemented exclusively on the element specified in the contract — without leaking to unintended parent or child containers.

*Validation Approach:*
```
grep_search for the activation point identifier (e.g., attribute, event handler, class)
in all component files, verifying that it appears only on the correct elements.
```

### 6.2 Verification of Isolation Mechanisms

- **Mandatory Check:** For each pair of interactive levels, verify that the isolation mechanism specified in the contract is present and active in the code — preventing interaction at one level from propagating or activating handlers at another level.

*PASSED Criterion:* The isolation mechanism (e.g., propagation block, guard condition, metadata check) is present and called before any event processing in the child level.

### 6.3 Verification of Type Identification

- **Mandatory Check:** For each interaction response handler, verify that there is a check for the event type or origin before processing it — ensuring that the handler of the correct level only processes events that belong to it.

*PASSED Criterion:* Every interaction response function checks the origin or type of the event as the first condition, before executing business logic.

*Note: The exact grep or inspection commands depend on the technology stack. The Validator must derive them from the contracts in `architecture.md` and adapt them to the project standard (e.g., HTML5 attributes for native DnD, event.target for DOM events, data types for messages in communication systems).*
